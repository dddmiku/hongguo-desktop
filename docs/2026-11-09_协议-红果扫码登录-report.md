# 红果 PC 与 TV 扫码登录协议

已实现 PC 独立扫码服务。2026-11-10，用户实际扫描 PC 二维码并在手机确认，隔离验证进入 confirmed：手机账号、历史、收藏均可读，读到历史 1438 条、收藏 3 部。官网授权 Cookie 已通过现有手机接口兼容验证。TV 实现另行进行设备扫码验证，不将 PC 结果写成 TV 设备通过。范围与时间线见 [qr-login-scope.md](qr-login-scope.md)。

## 官方请求与字段

| origin | path | 方法 | 参数字段 | 返回字段与状态 |
| --- | --- | --- | --- | --- |
| https://hongguoduanju.com | /passport/web/get_qrcode/ | GET | aid、next、language、is_from_ttaccountsdk、passport_jssdk_version、passport_jssdk_type、account_sdk_source | data.token、data.qrcode、data.expire_time、data.error_code |
| https://hongguoduanju.com | /passport/web/check_qrconnect/ | GET | 同上，加 token | data.status、data.redirect_url；new、scanned、confirmed、expired |

当前官网 Passport 请求应用 ID 为 `513755`，现有手机内容接口为 `8662`。官网公共源码中的其他业务应用 ID 不能直接当作扫码 Passport 应用 ID：使用错误 ID 时虽然二维码创建成功，轮询会报 `2035`。

直接把官网二维码应用 ID 改为手机 `8662` 的只读探针返回 `data.error_code=16`，没有二维码。因此手机会话交接必须由正式官网授权后的候选登录态校验来确认，不能通过替换应用 ID 省略这一环节。

二维码为服务端返回的 PNG/JPEG base64 图片，`expire_time` 为绝对秒时间。客户端只接收二维码图片和独立生成的本机请求 ID。轮询 token 与授权跳转地址始终留在 Python 服务内存。

## 接入 PC

`service/qr_login.py` 暴露 `QrLoginManager(account, commit_session, current_identity)`。方法为 `create()`、`status(id)`、`cancel(id)`、`close()`。

返回公共字段：`id`、`status`、`expiresAt`、`pollAfter`、`message`；创建或二维码轮换时附 `imageDataUrl`。终态成功返回 `session`，失败返回固定文案的 `error`。状态为 `waiting`、`scanned`、`verifying`、`confirmed`、`expired`、`cancelled`、`failed`。

`commit_session(candidate, origin_identity)` 由 Provider 实现，必须在已有账号写锁内重新核对起始身份，再保存 DPAPI 登录态并清理账号缓存。刷新二维码、账号切换、取消、服务退出和二维码到期都会丢弃旧授权上下文；旧在途请求无法覆盖新账号。

扫码确认后仅手动跟随 HTTPS 官方授权跳转，并逐跳检查 host/path。候选凭据只取认证 Cookie，CSRF Cookie 单独存在时不算登录。之后显式使用候选会话调用现有签名手机接口：

1. `/reading/user/info/v`：读取手机账号 UID，拒绝游客标识。
2. `/reading/bookapi/read_history/list/v`：检查手机历史可读。
3. `/reading/bookapi/bookshelf/video/list/v`：检查手机收藏可读。

三项全部通过才执行提交回调。任一失败保留当前账号，返回 `QR_MOBILE_SESSION_UNAVAILABLE`。首轮验证只覆盖三读，没有对手机历史或收藏做写入。

## TV 适配

实际 TV 工程为 `C:\Users\dddmiku\Desktop\codex\hongguo-tv`。其 `AccountApi` 使用同一 Cookie/x-tt-token 与手机应用 ID，因此可用 Java 实现相同扫码协议，不需要 TV WebView 或浏览器常驻。

TV 已增加进程内候选会话工厂、`AccountApi.verifyQrCandidate`、`QrMobileVerifier` 与独立扫码网络请求，使用现有签名内容请求检查账号、历史与收藏。验证后的候选账号由 `Account.commitQr` 在账号锁内复核后保存。现有 `historyPage(Account, ...)` 会检查候选是否等于已保存会话，扫码验证使用单独的三读路径；通用播放器 HTTP 没有改变。TV 设备实扫仍待独立执行。
